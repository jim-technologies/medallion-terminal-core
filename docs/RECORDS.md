# Record Workspaces

Medallion's record layer provides the reusable frontend primitives behind
spreadsheet-style databases, lightweight CRM, project delivery, inventory,
case management, intake, and approval workflows. It is intentionally generic:
the framework understands fields, records, views, links, context, revisions,
and action capabilities—not customers, deals, tasks, or any vendor's product
model.

Run the reference workspace with:

```bash
flox activate
pnpm backend &
pnpm dev
```

Open:

```text
http://localhost:5173/?template=/examples/work-management.json&backend=http://localhost:3001
```

## One model, multiple projections

| Capability | Built-in projection | Contract |
|---|---|---|
| Typed rows and inline edits | `record_grid` | `RecordSetPayload` |
| Grouped workflow lanes | `record_board` | The same `RecordSetPayload` |
| Date-based planning | `record_calendar` | The same `RecordSetPayload` |
| Schema-driven create/edit/detail | `record_form` | The same `RecordSetPayload` |
| Saved filters, sorts, and field visibility | `RecordView` | Backend-declared, frontend-applied |
| Linked records and cross-widget drill-down | Link field values + record `context` | Shared dashboard `ctx` |
| Governed create/update/delete | `RecordCapabilities` | `SubmitAction` / `WatchAction` |
| Formula, lookup, and rollup display | Computed field types | Backend-computed, read-only |
| Grid/list/board/calendar/gallery/timeline/form metadata | `RecordViewType` | Built-in or custom projection |

The grid, board, calendar, and form do not maintain separate copies of the
business model. A row selected anywhere sets `ctx.record_id`; every sibling
projection can follow that selection. A successful mutation emits standard
action telemetry and refreshes the workspace so every view converges on the
same backend state.

## Canonical payload

```jsonc
{
  "workspace_id": "operations",
  "table_id": "work_items",
  "table_name": "Work items",
  "primary_field": "name",
  "fields": [
    {
      "key": "name",
      "label": "Work item",
      "type": "RECORD_FIELD_TYPE_TEXT",
      "required": true
    },
    {
      "key": "customer",
      "label": "Customer",
      "type": "RECORD_FIELD_TYPE_LINK",
      "linked_table_id": "customers"
    },
    {
      "key": "stage",
      "label": "Stage",
      "type": "RECORD_FIELD_TYPE_SINGLE_SELECT",
      "choices": [
        { "value": "planned", "label": "Planned", "color": "info" },
        { "value": "active", "label": "Active", "color": "warn" },
        { "value": "done", "label": "Done", "color": "ok" }
      ]
    },
    {
      "key": "margin",
      "label": "Margin",
      "type": "RECORD_FIELD_TYPE_FORMULA",
      "format": "percent"
    }
  ],
  "records": [
    {
      "id": "work-42",
      "revision": "7",
      "values": {
        "name": "Northstar onboarding",
        "customer": {
          "id": "customer-9",
          "label": "Northstar Foods"
        },
        "stage": "active",
        "margin": 0.34
      },
      "context": {
        "customer_id": "customer-9"
      }
    }
  ],
  "views": [
    {
      "id": "delivery",
      "name": "Delivery",
      "type": "RECORD_VIEW_TYPE_BOARD",
      "group_by": "stage",
      "visible_fields": ["customer", "margin"],
      "filters": [
        { "field": "stage", "operator": "neq", "value": "done" }
      ]
    }
  ],
  "active_view_id": "delivery",
  "total": "1",
  "capabilities": {
    "create": true,
    "update": true,
    "delete": false,
    "create_action_id": "record_create",
    "update_action_id": "record_update",
    "delete_action_id": "record_delete"
  }
}
```

Proto JSON uses lower camel case when generated by standard protobuf
libraries. Hand-authored JSON and lightweight adapters often use snake case.
The built-ins normalize both at the boundary.

## Field behavior

Supported field types cover text, long text, numbers, currency, percentages,
booleans, dates, datetimes, single/multi select, users, links, attachments,
URLs, email, phone, formulas, lookups, rollups, and created/updated timestamps.

Important invariants:

- Stable field `key` values are storage identifiers; labels may change.
- Formula, lookup, rollup, created-at, and updated-at fields are always
  read-only in the standard widgets, even if a payload accidentally marks
  them writable.
- Attachment fields are displayed by the record widgets but writes should be
  routed through a host upload flow, usually `file_browser` or a custom field
  editor backed by `SubmitAction`.
- Choice colors are semantic hints. The UI maps them onto the theme's status
  roles; payloads do not inject arbitrary CSS.
- Link values should be `{id, label}` or arrays of that shape. The label is
  presentation; the id is identity.
- A link field may declare `choices` for a bounded selector. Large linked
  tables should use a host search/autocomplete field editor and let the
  backend resolve submitted ids to authorized labels.
- Record `context` may expose safe navigation keys such as `customer_id`.
  Selecting the record merges them into dashboard context, allowing object
  detail, charts, files, or actions to retarget without direct widget
  coupling.

A backend may omit `fields` for a quick prototype; the normalizer derives a
basic schema from row values. Production applications should declare fields
explicitly so validation, formatting, permissions, and migrations stay
deterministic.

Projection-specific options stay deliberately small:

- `record_board.options.allow_move` defaults to `true`. Set it to `false` for
  read-only workflow projections even when the payload advertises update
  capability. Moves still require a writable grouping field and `backendUrl`.
- `record_calendar.options.color_field` may name a single- or multi-select
  field. Event dots use that field's declared choice colors; values are never
  interpreted as domain-specific statuses.

## Saved view semantics

`RecordView` is portable metadata, not a query language. It supports:

- `visible_fields`
- `group_by`
- `date_field`
- `title_field`
- ordered `sorts`
- AND-combined `filters`

Portable filter operators are `eq`, `neq`, `contains`, `in`, `gt`, `gte`,
`lt`, `lte`, `empty`, and `not_empty`.

Small result sets can return records once and let each widget apply the saved
view locally. Large or sensitive tables should apply views, search, policy,
and pagination on the server and return only the authorized page. `total` and
`next_page_token` are available for that contract. Never rely on a client-side
filter to hide data a user is not allowed to read.

Grid, list, board, calendar, gallery, timeline, and form are canonical view
types. Grid/list, board, calendar/timeline-date projection, and form have
built-in renderers. A host can register a custom gallery or timeline renderer
against the same payload without changing its backend model:

```tsx
registerWidget('record_timeline', RecordTimeline)
```

## Mutation contract

All writes use the existing action transport. Widgets submit these parameter
shapes:

```jsonc
// create
{
  "workspace_id": "operations",
  "table_id": "work_items",
  "values": { "name": "New item", "stage": "planned" }
}

// partial update
{
  "workspace_id": "operations",
  "table_id": "work_items",
  "record_id": "work-42",
  "revision": "7",
  "values": { "stage": "active" }
}

// delete
{
  "workspace_id": "operations",
  "table_id": "work_items",
  "record_id": "work-42",
  "revision": "8"
}
```

Successful create/update responses should include identity and the new
revision:

```json
{
  "id": "action-123",
  "status": "ACTION_STATUS_OK",
  "data": {
    "record_id": "work-42",
    "revision": "8"
  }
}
```

Backends must:

1. Authorize the workspace, table, action, record, and individual fields.
2. Treat `client_request_id` as an idempotency key and return the original
   result on retries without applying the write twice.
3. Compare `revision` for update/delete and return
   `ACTION_STATUS_REJECTED` on a stale write.
4. Reject unknown, read-only, or malformed fields.
5. Validate required fields and domain rules after applying defaults.
6. Compute formulas, lookups, rollups, timestamps, and automation effects on
   the server.
7. Record actor, before/after values, policy decision, action lifecycle, and
   request id in a durable audit log.
8. Return only the fields and linked labels the caller may read.

Asynchronous automations can return `ACCEPTED` or `PENDING`; the generic
mutation hook follows `WatchAction` until a terminal status. The reference
backend demonstrates synchronous CRUD and revision conflicts.

## Production architecture

`TerminalService` remains the frontend adapter. A production host usually
composes:

- schema and migration storage;
- transactional record storage and indexed query;
- row-, record-, and field-level policy;
- identity, teams, and user directory;
- formula/lookup/rollup evaluation;
- attachment storage and malware scanning;
- comments, mentions, activity history, and notifications;
- durable automations, webhooks, schedules, and approval state;
- real-time collaboration and conflict resolution;
- audit, retention, export, and data-residency controls.

Those are deliberately not implemented in this frontend package. The stable
record payload, action lifecycle, context wiring, widgets, exports, stories,
and integration tests are the frontend seam for adding them incrementally.

## Extension rules

- Prefer a new `RecordView` or widget option when the data model is unchanged.
- Register a custom widget when a domain needs a different projection.
- Add a field type only when its edit/display semantics are broadly reusable.
- Add a new canonical payload only when the identity or lifecycle model is
  genuinely different from records.
- Keep domain names in templates and backend schemas, not framework code.
- Keep authorization and computed truth on the backend; templates only
  describe presentation and interaction.
